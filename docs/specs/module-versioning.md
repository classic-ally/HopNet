# RFC-020: Schema Evolution — Chain-Based Migration of the Module Schemas

**Status**: Draft (2026-08-16). Supersedes this file's 2026-07-23 draft
in place — the module graph and the flat-ordinal argument carry
forward; the mechanism is redesigned post-RFC-019
**Depends on**: RFC-019 (epoch boundaries, certified snapshots, the S6
boot transition, S7 join), RFC-016 (projection registry — the seam
module chains register through)
**Amends**: RFC-019 (boot gates 3–4, the S6 node-local carry,
"`initialize` redeemed as the permanent fresh-schema installer",
"adjacent-version readable" — each amended in §RFC-019 Amendments)
**Unblocks**: treating the existing mesh as non-disposable (schema no
longer frozen at first external deployment); client-compat v2
replicated visibility (its
Open Question 1, snapshot format tolerance, is discharged here)
**Related**: RFC-021 (nix upgrade provider — stages the binaries whose
boundary crossing this RFC gives migration content to);
RFC-023 (client-compat — the orthogonal client↔node version axis)

## Summary

Every module's schema is defined by an append-only chain of frozen,
deterministic migration files; a module's chain position doubles as its
snapshot section `format_version`. One mechanism consumes the chain
everywhere: fresh installs replay it from its baseline; upgrading nodes
fast-forward their copied sealed database upon restart into a new
version; joiners rebuild the artifact's ordinal by replay, import the
certified snapshot — the current epoch's genesis state — then
fast-forward and replay the epoch's decided blocks. `initialize` is
deleted; the chain is the only installer. Live code only ever sees the
newest schema — intermediate shapes exist solely as SQL executing
inside the boot transition, before the node is live.

## Motivation

- **HopNet still has no migration path.** `initialize`
  (`src/db/shared.rs:268`) is one monolithic `execute_batch` of the
  current binary's whole schema, `is_schema_initialized`
  (`src/db/shared.rs:59`) is a boolean probe, and the workspace
  contains zero `ALTER TABLE`. Schema changes ship by recreating
  meshes.
- **RFC-019 unfroze other surfaces.** Handler semantics, payload
  encodings, the block envelope, wire formats, genesis-fixed config —
  all per-epoch concerns now. Existing replicated tables still cannot
  evolve across an epoch boundary:
  - the importer demands exact canonical-column equality
    (`common/src/snapshot.rs:397`, `import_section`) — even an added
    nullable column is refused
  - bumping a section `format_version` skips the whole section, and
    the boot transition treats any skip as fatal
    (`src/regenesis/boot.rs:805`)
- **The epoch boundary is now a clean schema migration point** — no
  block encoded under old rules is ever applied by a new binary.
  Migration code runs once, deterministically, on certified input, on
  every node at the same height.
- **The non-disposable mesh already exists.** We operate a mesh worth
  keeping that is still inside the `initialize` regime, so a one-time
  exit is a deliverable of this RFC, not future-proofing. The design
  makes that exit an ordinary upgrade regenesis: the first chain-based
  release's baseline is generated byte-identical to today's schema, so
  the existing mesh crosses into the chain regime with zero migration
  steps (§Cutover).

## The Model

- **One schema per binary.** A binary's live schema is the newest
  ordinal of every module chain it embeds. No live code path reads or
  writes an older shape — older shapes exist only as SQL executing
  inside the boot transition.
- **Replay defines the schema.** "Module M at ordinal k" describes an
  empty database with M's migration files baseline..k applied in
  order. Every
  shape comes from replay; a fresh install replays to the newest
  ordinal, a joiner replays to the artifact's older one. No DDL or
  second definition outside the chain to drift from it.
- **Ordinals are flat integers.** An ordinal encodes chain position
  and carries no semver-style compatibility semantics. Multiple
  ordinal bumps can land between release cuts. A change in ordinal is
  the sole authority for the existence of a schema change.
- **A module's ordinal IS its snapshot section `format_version`.** A
  section's canonical encoding derives from the schema (columns
  serialize name-sorted), so the ordinal already determines the wire
  shape. Consequences:
  - the artifact manifest already records, per section, exactly which
    ordinal a joiner must replay to before importing
  - any schema change to an exported table forces an ordinal bump,
    since it changes the wire shape — mechanical, CI-enforced
    (§Validation & Tripwires)
- **Three version axes, one upgrade pipeline.** All three are
  monotonic — they differ by role, not shape:
  - **release version (CalVer code) — availability synchronization**:
    can every seated validator run the target? Staged attestations and
    the propose-time precondition (RFC-019/021); API consumer
    versioning also rides this axis, since releases are cut along this
    seam (client-compat)
  - **epoch — crossing synchronization**: when does every node cross?
    One decided boundary, same height everywhere (RFC-019)
  - **schema ordinal (per module) — crossing semantics**: what happens
    to the data at the crossing? Which chain steps fast-forward (this
    RFC)
  - a release embeds one newest ordinal per module; many releases ship
    the same ordinals; ordinals advance on a live mesh only at a
    boundary

## Module Boundaries & Ownership

- **Modules are the unit of versioning.** Each owns a baseline
  (`NNNN_init.sql`), a chain, and one ordinal. Coherent only because
  the module graph is acyclic — a cycle would make every bump
  multi-module by default.
- **Ordered by data dependency, not crate dependency.** FK direction
  decides the layering, and the two graphs invert: `users`/`nodes`
  live in the host crate — RFC-016's composition root, top of the
  crate graph — but every projection references them, which puts them
  at the bottom here. The inversion is why the host crate cannot be
  one module — and why a module is a schema-ownership unit, not a
  crate: `identity` and `telemetry` stay host-crate code and become
  modules by receiving a baseline and a chain.
- **The graph**, at module altitude — the snapshot registry
  (`src/db/snapshot.rs`) enumerates table membership and is the single
  source of truth; replay order is manifest order, which is FK
  direction:

      consensus   (FK-isolated: references nothing, referenced by nothing)
      identity    (users, nodes, this_node, sequences, device_tokens, …)
         ├─ telemetry   (→ nodes)
         ├─ takeout     (→ users)
         └─ storage     (→ nodes)
              ├─ drive    (→ users, data_blocks)
              └─ photos   (→ users, data_blocks, device_tokens)

  - **runtime read paths are not graph edges**: takeout materializes
    drive and photos data through their own `ProjectionExporter`
    implementations — each module renders its own section against the
    live schema, so no schema knowledge crosses the module boundary;
    the graph tracks FK ownership only
- **Identity and telemetry seams become explicit.** Previous work
  deferred their refactor from the monolithic `execute_batch`; tables
  are split into the two chains at this point.
- **No table without an owner.** Registry classification — already
  mandatory for every table, test-pinned against `sqlite_master` —
  grows an owning-module field. A table outside a chain fails CI.

## The Chain — Format & Authoring Contract

- **Layout.** Each module's chain is a folder of step files,
  `migrations/<module>/NNNN_slug.sql`, living beside the code that
  owns it and embedded into the binary at compile time. The
  lowest-numbered step `NNNN_init.sql` is the baseline — `0000` for a
  module born in the chain regime, the adopted pre-chain
  `format_version` for cutover baselines (§Cutover). The host
  assembles chains through the registry, in manifest order.
  - **sequential `NNNN`, not timestamps, as it acts as high-water
    mark.** A module's recorded position is only the ordinal
    (`format_version`), so we have no applied-set tracking, beyond the
    high-water mark.
  - **a step sorting before the released head is silently skipped** —
    fast-forward applies "steps after k", so a late-merging step with
    an early name never runs on any mesh already past it. Timestamp
    naming would allow clean merges but result in unsafe behaviour.
  - **review ordering during merge collisions.** Parallel branches
    minting the same ordinal collide at CI — different slugs merge
    cleanly in git, so the duplicate-ordinal check supplies the loud
    conflict — forcing the "do these steps commute?" question while it
    is still cheap. Last merger gets renumbered, as renumbering is
    free before merge, but must be locked afterwards.
  - **the latest release tag freezes the chain.** Only a cut release
    is ever deployed, so only released steps can have been crossed by
    a mesh. CI diffs the tree against the latest release tag: steps
    below the head must be byte-identical, new steps strictly
    ascending and contiguous, duplicate ordinals refused, and
    redefinition of a released step only via an explicit reviewed
    marker (§Validation & Tripwires).
- **One file per ordinal.** Step NNNN carries everything that ordinal
  changes — DDL and row transformations together, applied in order.
- **SQL by default, Rust by exception.** A step is a `.sql` file
  unless the transformation cannot be expressed in SQL (re-encoding a
  blob column, recomputing a hash); then it is a registered Rust `fn`
  occupying the same position in the ordinal sequence, held to every
  rule below, and justified in review.
- **The contract** — rules every step must satisfy, numbered for
  citation:
  1. **Frozen once released.** A step included in a release tag is
     never edited — CI enforces byte-identity against the latest tag.
     Redefinition (the explicit marker) is legal only for a step no
     mesh has crossed: a deterministic wedge at a boundary is
     recovered by a patched release redefining the step — nobody
     crossed, so no history forks.
  2. **Deterministic.** No wall clock, no randomness, no environment
     reads, no nondeterministic ordering. Every node replays the same
     step independently and must land byte-identical logical state.
  3. **Seeds are legal.** A step may insert rows — literal values
     only, per rule 2. The joiner path truncates exported tables (of
     sections the artifact contains) between replay and import, so
     replayed seeds never collide with the artifact (§Execution).
  4. **Write your own module; read upstream only.** A step writes
     only its owning module's tables and may read modules earlier in
     manifest order — always already fast-forwarded when it runs.
     Multi-module changes are one step per module, coordinated by
     manifest order, never by a shared ordinal.
     - known tension, tolerated: `this_node` (identity's node-local
       singleton) carries storage- and upgrade-owned settings
       columns. Live code may keep reading them across modules, but
       adding such a column via a step is identity's to do — another
       module wanting one requests an identity step, or the columns
       eventually migrate to a module-local table.
- **Out of contract, refused by CI.** Serialization-config changes to
  a released table (`excluded_columns`, table role) and `DROP TABLE`
  are not yet supported — the chain records schema history, and the
  joiner path would also need *config* history to consume them (Open
  Questions). CI refuses them until that gap is designed.

## Execution — The Seam

- **This RFC adds no trust decisions.** Every chain operation runs
  after RFC-019's gates — version, lineage, hash verification — have
  accepted the input. Who to trust and when to cross stay RFC-019's
  business; the chain defines what happens to accepted data.
- **Two primitives:**
  - **replay** — materialize a module's schema at ordinal k by
    applying steps baseline..k to an empty database
  - **fast-forward** — validate a database's recorded ordinals and
    schema fingerprint, then apply the steps from there to the
    binary's head
- **Three insertion points in RFC-019's flows:**
  - **the upgrade boot transition** (`regenesis::boot`; RFC-019 S6):
    - copy the sealed database, fast-forward the copy
    - consensus-history tables are emptied in the copy, selected by
      registry table role, never a hand-written list
    - the sealed original is never touched, so rollback stays
      possible until the new epoch decides its first block
  - **the epoch join** (RFC-019 S7), split by what the joiner brings:
    - **from nothing (fresh join)**: replay each chain up to the
      ordinal the artifact's manifest names — the database now has
      the shape the artifact was written in. Node-local tables keep
      replay's rows: they're absent from the artifact, so there is no
      certified authority to replace them (`this_node` is seeded by
      the join ceremony, as today)
    - **from an existing database (diverged rebuild, multi-epoch
      straggler)**: copy it — node-local state (`this_node`, pins,
      inventory) is precious and rides the copy — and fast-forward
      the copy to the artifact's ordinals (a straggler's shape is
      older than the artifact's)
    - **both then splice in the checkpoint**: empty the exported
      tables of every section the artifact contains — this discards
      only rows the artifact replaces: replayed seeds on the fresh
      path (the artifact carries their certified, evolved
      descendants — a checkpoint of *all* rows), stale or diverged
      replicated state on the rebuild path. A module absent from the
      artifact — introduced at this very boundary — keeps its rows:
      no checkpoint exists, and contract rule 2 makes replayed seeds
      identical to the seeds live nodes planted at the crossing
    - import the artifact and verify its hashes while the database
      still has the artifact's shape — the certified hashes were
      computed over that shape, so verification cannot run after
      migration
    - fast-forward to the binary's head; the whole build is one
      transaction, so failure anywhere leaves no half-built database
  - **fresh install** (mesh creation; any first boot):
    - replay every chain to head — this IS the installer; `initialize`
      is deleted, and RFC-019's gate 3 ("current binary's full schema
      via `initialize`") now means the replay (§RFC-019 Amendments)
- **Everything runs pre-live.** All insertion points sit inside the
  boot transition — before the pool opens, before the engine spawns,
  before any route answers. No API surface ever observes an
  intermediate shape.

## RFC-019 Amendments

- **Boot gate 3 (import).** The import no longer targets the current
  binary's schema: the target database is replayed to the artifact's
  ordinals, verification runs there (recompute per-section hashes
  against the manifest, in the artifact's own shape — unchanged), and
  the fast-forward to head follows inside the same transaction.
- **Boot gate 4 (node-local carry): deleted.** Both of its customers
  are served by copies instead: the upgrade path trivially (the whole
  sealed database is the copy), the rebuild path via copy +
  fast-forward to the artifact's ordinals + checkpoint splice
  (§Execution). Node-local schema evolves through the same chain as
  everything else; the gate's "hook point for RFC-020's ordinary
  linear migrations" is discharged — the hook is the chain.
- **The S6 build for the sealing node.** Fresh database + certified
  import is replaced by copy + fast-forward. The `build_next`
  crash-safe state machine, the atomic swap, and the rollback marker
  survive unchanged — only the content construction inside the
  transaction changes.
- **"`initialize` redeemed as the permanent fresh-schema installer"**
  (gate 3's parenthetical): superseded — replay is the permanent
  installer, and `initialize` is deleted.
- **"Adjacent-version readable" becomes chain-readable.** The
  snapshot format's compatibility promise no longer rests on
  skip-with-report tolerance between adjacent versions: any artifact
  whose section ordinals appear in a released chain is readable, by
  replaying to those ordinals. Skipped sections at boot remain fatal
  — under the chain, a skip can only mean corruption or hostility,
  never legitimate version skew.
- **Staged join: the version gate still runs first.** A straggler
  stages its downloaded artifact while still running the old binary;
  the rebuild waits until its operator installs the required version.
  RFC-019 justified this ordering by the node-local carry, which is
  now deleted — the standing reason is the chain itself: steps ship
  inside binaries, so the old binary does not contain the steps the
  rebuild needs. Wrong version parks the node with staging kept and
  database untouched, exactly as today.

## Version Surfaces

- **In the database: a node-local ordinal stamp.** A small meta table
  records each module's current ordinal — the fast-forward's
  validation input. Module names are section names: the registry
  (`src/db/snapshot.rs::sections()`) is the sole enumerator, and the
  stamp is validated against it at boot. Node-local role: the
  artifact carries its own ordinal record (the manifest), and the
  stamp describes *this file*, not consensus state.
- **In the snapshot artifact: inline, per section.** The artifact —
  the serialized snapshot file written at seal and fetched by joiners
  (RFC-019) — labels each section it contains with the module name
  and `format_version`, which IS the ordinal (§The Model). A joiner
  reads its replay targets from the file it is importing; no new
  field, no side channel.
- **In operator surfaces**: the status view and debug routes report
  per-module ordinals beside epoch and version; divergence reports
  name section and ordinal. Operators debugging a boundary see one
  vocabulary everywhere.
- **Never client-visible.** No DeviceToken surface, API payload, or
  health body carries a module ordinal. client-compat forbids clients
  branching on node capability — API consumer behaviour is tied
  solely to the advertised release version (the CalVer floors) — so
  module ordinals stay off the wire entirely.
- **Takeout archives: stamped, not versioned.** Exporters record the
  producing module's ordinal in each archive section at export time —
  cheap provenance for any future archive-import guard. Archive
  format evolution itself stays out of scope (Non-Goals).

## Cutover

The one-time exit from the `initialize` regime (Motivation), shipped
as part of this RFC:

- **Baselines are generated, not written.** Each module's baseline
  is extracted from what `initialize` and the module installers build
  today; while both regimes coexist in the PR, a parity gate proves
  replay lands byte-identical (canonicalized `sqlite_master`) to the
  old installer. Only then is `initialize` deleted — and the parity
  reference becomes a generated, checked-in schema snapshot, kept for
  readability and CI-verified thereafter.
- **Baseline ordinals adopt the existing numbering.** Sections
  already carry `format_version`s — the field has been an ordinal
  without a chain all along. Each surviving section's baseline starts
  at its current value, so a cutover-epoch artifact needs no number
  translation; the baseline file takes the ordinal as its number
  (`drive/0001_init.sql`, and `consensus/0002_init.sql` after its S1
  covered-set move bumped it 1→2). The new `identity` and `telemetry`
  sections start at 0 — their lineage from `host@3` is recorded by
  the one-time mapping, not by fake numbering.
- **The host section split reaches the mesh at this crossing.** The
  registry split landed at S1 (branch-internal); the cutover boundary
  is where a live mesh first observes it. A one-time import mapping —
  artifact section `host@3` feeds the `identity` and `telemetry`
  baselines, with `committed_tx_nonces` routed to `consensus`, each
  table to its new owner — serves joiners whose artifact was sealed
  pre-split. The upgrade path never notices (no import), and the
  mapping retires naturally: the first post-cutover seal writes the
  new sections, so it only ever fires for artifacts of exactly the
  cutover boundary.
- **Existing databases are stamped, not migrated.** Their shape IS
  the baseline by construction; the transition writes the ordinal
  stamp table, validates the schema fingerprint, and runs zero steps.
- **The crossing is an ordinary upgrade regenesis.** The old binary
  seals as usual; the new binary copies and fast-forwards nothing;
  RFC-019's rollback window is the safety net for the mesh we care
  about — the sealed database survives untouched until the new epoch
  first decides.
- **Rehearsed before real.** The orchestrator crosses a disposable
  mesh through the exact cutover — old release image to cutover
  release — before the live mesh does.

## Failure Modes

Ordered by when they can occur:

- **A step fails deterministically at a boundary** — bad SQL, a
  violated constraint: every node wedges identically at the same
  point; nothing crosses. Recovery is RFC-019's catastrophic-target
  playbook: roll back mesh-wide inside the window, or ship a patched
  release that redefines the step (contract rule 1 — legal, nobody
  crossed) and cross again.
- **A step succeeds but diverges** — rule 2 violated, nondeterminism
  slipped through review: the divergence checker or the next
  boundary's vote-iff-match surfaces it, and RFC-019's recovery
  applies — anomalous nodes rebuild via the epoch join. Per-step
  golden fixtures (§Validation & Tripwires) exist to catch this class
  in CI instead.
- **Crash mid-fast-forward**: the build is one transaction inside the
  boot state machine; retry from the sealed artifacts is idempotent
  (RFC-019 S6, unchanged).
- **Stamp or fingerprint mismatch at fast-forward** — the database
  does not match its recorded ordinals (corruption, operator
  surgery): refuse loudly and park; never guess. If the mesh has
  moved on, the node rebuilds via the epoch join.
- **Chain/binary skew: impossible by construction.** Steps are
  embedded at compile time; there is no runtime folder to drift from
  the binary that certifies it.

## Validation & Tripwires

CI, diffed against the latest release tag (the freeze boundary —
§The Chain):

- released steps edited: byte-identity required; redefinition only
  via the explicit `REDEFINES` marker (contract rule 1)
- a new step not strictly above its module's released head; duplicate
  ordinals anywhere; gaps — new steps continue +1
- a schema change without an ordinal bump: per module, HEAD's
  replayed schema differs from the tag's while the ordinal is
  unchanged
- an ordinal bump without a step file, or a step file without a bump
- serialization-config changes to released tables
  (`excluded_columns`, table role) and `DROP TABLE` — unsupported
  until the config-history gap is designed (§The Chain, Open
  Questions)
- a table outside a chain: the registry pin against `sqlite_master`,
  grown an owning-module field (Module Boundaries)

Test-level gates:

- **replay parity**: replaying every chain to head lands
  byte-identical (canonicalized `sqlite_master`) to the checked-in
  generated schema snapshot (§Cutover)
- **per-step golden fixtures**: each step ships a fixture database at
  its predecessor ordinal with representative rows, and the step's
  output is hash-pinned — the determinism net for contract rule 2
- **stamp validation**: fast-forward refuses a database whose
  fingerprint disagrees with its recorded ordinals (Failure Modes)

Orchestrator gates:

- the cutover rehearsal (§Cutover)
- a boundary with real migration steps: a node that lived through
  the crossing and a fresh joiner land logically byte-identical —
  the divergence checker as final arbiter
- an epoch join from an older-shaped artifact: replay, splice, and
  fast-forward exercised end to end over real containers

## Non-Goals

Each tracked, not forgotten:

- **sqlx, or any migration framework**: the chain must compose with
  the certified-import boot machinery and the synchronous rusqlite
  stack it lives in; adopting a framework is an orthogonal ergonomics
  decision, deliberately decoupled from this RFC
- **client capability negotiation**: module ordinals never reach
  clients (§Version Surfaces); API consumer behaviour keys on the
  release axis alone (client-compat)
- **takeout archive format evolution**: archives keep RFC-010's
  manifest versioning; this RFC only stamps archive sections with
  their producing ordinals (§Version Surfaces)
- **downgrades**: chains fast-forward only. Recovery from a bad step
  is RFC-019's rollback window or a redefining release (Failure
  Modes), never a reverse migration
- **global canonical-encoding changes**: `ARTIFACT_VERSION` business
  (§The Chain), never ordinal business
- **serialization-config evolution and `DROP TABLE`**: refused by CI
  until the config-history gap is designed (Open Questions)

## Implementation Slices

One PR, built and reviewed as ordered stages: each stage lands green
on the branch, and the branch merges only once S6 is complete. The
release that follows the merge IS the cutover release, so no
intermediate release ever ships a section change the live mesh cannot
cross.

- [x] S1 — chain machinery + parity: `migrations/` folders (generated
      baselines only), compile-time embedding, the replay primitive,
      and the parity gate proving replay ≡ `initialize`. Both regimes
      coexist.
  - landed with two recorded deviations, both decided at planning:
    - the SECTION SPLIT moved forward from S6: `host` dissolved into
      `identity`@0 + `telemetry`@0 at S1, so chains and sections never
      disagree on module names during S1–S5. S6 keeps only cutover
      mechanics. Registry goldens re-pinned at S1 (the seeded artifact
      length delta is exactly the section-header arithmetic, +25 —
      the cheap proof no table content moved)
    - `committed_tx_nonces` and `regenesis_state` moved to the
      CONSENSUS module: both FK-isolated and written only by consensus
      machinery; consensus `format_version` 1→2, baseline
      `0002_init.sql`. Section ownership only — their DDL stays in the
      host-generated consensus baseline; a module is a
      schema-ownership unit, not a crate
  - runner in `hopnet-common::chain`: caller-owned transaction,
    per-step SAVEPOINTs (a failing step reports module+ordinal with
    its partial effects undone); chains registered via a required
    `Projection::chain()` plus the host `db::chains` assembler
    mirroring `sections()`; explicit `include_str!` step arrays
  - baselines generated from `initialize` by a one-time bin, frozen,
    generator deleted in the same stage. SQLite strips `IF NOT
    EXISTS` from `sqlite_master` text, so dump-to-dump parity is
    exact by construction — the consensus installer's idempotent DDL
    needed no normalization
  - gates: byte-exact `sqlite_master` parity (replay ≡ initialize),
    chains≡sections mirror (names, order, head == format_version),
    classified-at-birth extended to indexes/triggers/views
- [x] S2 — installer swap: fresh install and mesh creation run on
      replay; `initialize` deleted; the generated schema snapshot
      checked in and the parity gate retargeted to it.
  - `db::chains::install` is THE installer (replay to head + the
    relocated validators shadowing gate). The monolithic batch, the
    per-crate installer batches (storage/drive/photos/takeout), and
    `Projection::install_schema` are all deleted — DDL text now exists
    only in the frozen baselines (the old installers' between-statement
    design prose lives in git history; in-statement comments survive
    in the baselines)
  - recorded nuance: hopnet-consensus KEEPS `install_schema` as its
    standalone/embedder installer — its chain lives host-side, out of
    the embeddable crate's reach. The spawn-time re-install in
    `SqliteStorage::from_handle` (a second DDL authority at every
    engine start) is deleted; `new()` keeps the convenience for
    owned-connection embedders, and a host-side pin
    (`consensus_standalone_installer_agrees_with_chain`) keeps the
    crate const agreeing with the chain
  - `migrations/schema.sql`: the generated, readable rendering of the
    current schema — regenerated via an explicit `#[ignore]` test
    named in the parity gate's failure message
  - `is_schema_initialized` survives unchanged (probes `this_node`);
    the S3 ordinal stamp replaces it
- [ ] S3 — ordinal stamp + fast-forward + the CI suite: stamp table,
      fingerprint validation, the release-tag tripwires, the
      golden-fixture harness.
- [ ] S4 — boot rework, upgrade path: copy + fast-forward replaces
      fresh + import + carry for the sealing node; prune derived from
      registry roles; the regenesis-restart orchestrator scenario
      stays green.
- [ ] S5 — boot rework, join paths: replay-to-manifest, the
      checkpoint splice, both joiner variants; the
      older-shaped-artifact orchestrator gate (fixture artifacts at
      back ordinals).
- [ ] S6 — cutover release: baseline-adoption verification, the
      cutover rehearsal scenario, release choreography — then the live
      mesh crosses. (The section split itself landed at S1; the
      `host@3` mapping lands with S5's join fixtures.)

## Open Questions

1. Historical serialization config: the joiner path needs config as
   of ordinal k (exclusions, roles, dropped tables) and the chain
   records only schema. Candidates: (a) make verification
   schema-and-artifact-driven — normalize `excluded_columns` away,
   let the certified artifact declare section membership, backstopped
   by the final hash check (recommended); (b) config deltas in step
   front matter; (c) registry tombstones. Until resolved, CI refuses
   the affected changes (§Validation & Tripwires).
2. Golden-fixture corpus: hand-written per step, or derived from the
   snapshotter's existing fixture data? Decide at S3.
